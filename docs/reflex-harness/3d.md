# 3D screenshot-only reflex contract

This mode renders the real first-person camera from `Racing3DWorld`, including hills and
banking. The player receives physical speed, but no 3D pose, elevation state, other physics
telemetry, centerline, checkpoint state, or racing line. The following controller fields are
derived only from the current or adjacent RGB screenshots:

| Field | Meaning |
| --- | --- |
| `vision_track_offset` | visible road-centre offset near the car |
| `vision_track_heading` | near-to-middle perspective road direction |
| `vision_bend_ahead`, `vision_bend_severity` | visible change in road direction across depth |
| `vision_visible_depth` | fraction of the view containing a plausible road corridor |
| `vision_left_gap`, `vision_right_gap` | image-space distance to each visible road edge |
| `vision_road_contact`, `vision_recovery_direction` | image-only contact and recovery cues |
| `speed` | physical engine speed, permanently exposed as the sole engine telemetry value |
| `vision_road_horizon`, `vision_horizon_shift` | camera-derived apparent road-plane and crest/dip cues |
| `vision_crest_risk` | visual warning that the road becomes occluded ahead |
| `vision_confidence` | fraction of sampled image rows containing a plausible road |

The elevation-related fields are camera-only. They measure the detected road's apparent
horizon and its change between frames, then flag when the road disappears behind a likely
crest. They do not raycast, read a depth buffer, access the terrain surface, or return
physical grade.

`inspect_perspective_road` returns the current five-depth image road profile. It is an
inspection of pixels, not an optimal path, track location, or steering command.

## Predictive overlap mode

`vision-3d-predictive-skills` overlaps a slow model call with the currently active
controller. The request includes the response-time horizon and asks the model to predict a
coarse activation state before selecting one of six reusable feedback skills:
`follow_lane`, `prepare_turn`, `take_turn`, `take_hairpin`, `recover_track`, or `stabilize`.
The model does not emit an open-loop key sequence.

Every skill reads a fresh first-person frame and physical speed each tick. When the answer
lands, the scheduler compares its predicted speed, visual road offset, visible bend, and road
contact with the then-current values. An obsolete answer is recorded and rejected; the prior
skill remains active. Prediction and validation use exactly the fields in the table above—no
simulator rollout, centerline, pose, map, or elevation telemetry.
